# 派工 prompt 模板

> 用法：複製對應模板，填掉【】，貼進 Agent 工具的 prompt。
> 每份模板都含三件套：目標與動機／驗收條件／回報格式。subagent 是全新 context，**它看不到你的對話**，所有背景都要寫進 prompt。

## 1. 搜尋／定位（subagent_type: `Explore`，model: `haiku` 或 `sonnet`）

```
在 /Users/kang/Downloads/KANG-agent 裡調查：【要找什麼，例如「書籍封面圖是在哪裡下載與快取的」】。
背景：【為什麼要找，例如「封面偶爾變問號，要先知道流程才能修」】。
重點檔案可能在【目錄提示，例如 小書蟲/小書蟲-web/】，但不要只看這裡。
驗收條件：至少用兩組不同關鍵字各搜一次（回報用過的搜尋詞），每個找到的位置都附行號。
回報格式：
- 結論（3 句以內，說流程怎麼走）
- 位置清單：檔名:行號 ＋ 每項一句說明
- 不確定的地方單獨列出
不要貼大段程式碼。
```

## 2. 實作（subagent_type: `general-purpose`，model: `sonnet`）

```
任務：在【檔案路徑】實作【功能描述】。
動機：【使用者要什麼、為什麼】。
背景與約束：
- 本專案風格：Vanilla JS（或【實際技術】）、預設不加註解、不要引入新依賴
- 【已知的相關位置：檔名:行號】
- 不要動【不該碰的範圍】
驗收條件：
- 【客觀可驗證的行為，例：「離線時按同步會顯示提示而不是靜默失敗」】
- `node --check 【檔案】` 通過（或【對應驗證指令】）
回報格式：改了哪些檔（檔名:行號範圍）、每處一句為什麼、驗證跑了什麼與結果、有無未解決的疑慮。
```

## 3. 重構（subagent_type: `general-purpose`，model: `sonnet`）

```
任務：重構【範圍，例如 app.js 的同步相關函式】，目的是【例如「消除三處重複的上傳邏輯」】。
硬性約束：
- 行為不可改變：重構前後，【列出必須不變的可觀察行為】
- 不改公開介面／不改【指定範圍】以外的檔案
- 分小步做，每步可獨立驗證
驗收條件：
- 【驗證指令】通過
- diff 中沒有無關改動（順手改格式、順手改命名都算違規）
回報格式：改動摘要（每步一行）、行為不變的驗證方式與結果、放棄沒做的部分與原因。
```

## 4. 研究（subagent_type: `general-purpose`，model: `sonnet`；需要查網頁時明說可以用 WebSearch/WebFetch）

```
問題：【要回答什麼，例如「Cloudflare Workers 免費方案的 CPU 時間限制，以及超過會怎樣」】。
動機：【要用這答案做什麼決定】。
要求：
- 以官方文件為準，附來源 URL；找不到官方說法就明講
- 區分「文件寫的」與「你的推論」
驗收條件：問題的每個子項都有答案或明確標註查不到。
回報格式：直接答案（先講結論）→ 依據與 URL → 對【我們的決定】的建議（1 段）。
```

## 5. 審查（subagent_type: `general-purpose`，model: `sonnet`；高風險用 `opus`）

```
審查對象：【diff / 檔案路徑 / 剛完成的功能】。
背景：【這個改動要達成什麼】。
用挑錯的立場審，不要客氣。依序檢查：
1. 正確性：有沒有輸入會讓它出錯（邊界、離線、並發、空資料）
2. 安全：有沒有把 key/URL/個資帶進會被 commit 或公開的地方
3. 一致性：與周圍程式碼的風格、與 CLAUDE.md 的約束有無衝突
驗收條件：每個問題都給「怎麼觸發」的具體情境，不接受「可能有問題」這種空話。
回報格式：問題列表（嚴重的在前：位置＋一句描述＋觸發情境＋建議修法）；沒問題的面向一句帶過。最後一行給總判定：可交付／需修。
```

## 通用注意

- 一次派多個獨立任務時，同一則回覆裡並行呼叫 Agent，省時間。
- subagent 回報不合格式 → SendMessage 追問一次；還是不行就自己收尾，不要無限追。
- 模板可以改，但「三件套」三個欄位不准刪（見 [維護協議.md](維護協議.md)）。
