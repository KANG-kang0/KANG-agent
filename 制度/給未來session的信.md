## 三件使用者沒問、但你必須知道的事

### 1. 這裡的「使用者」是誰，決定你所有方案的形狀
KANG 是獨立開發者，不是全職工程師團隊：專案都是一人維護、跑在免費額度上（Cloudflare、Supabase、Railway free tier）、給自己和家人朋友用（短線衛兵是給爸爸的）。所以：
- 永遠優先選**零維運、免費、少依賴**的方案；任何「要一直顧著」的基礎設施都是錯的建議。
- 溝通用白話中文，講清楚「做了什麼、怎麼驗證、下一步」；不要甩術語。
- 功能價值 > 程式潔癖。不要主動提議大重構；app.js 三千行是刻意的取捨，不是待辦。

### 2. 小書蟲真正的結構性風險是 key 的位置
目前 Claude API key 的安全模型依賴「部署 URL 不外流」。這在「只有自己用」階段成立，但使用者的計畫是分享給朋友、將來商業化——**在任何形式的推廣之前，key 必須完全退到 proxy Worker 後面＋加用量上限**。repo 裡已有 `小書蟲/小書蟲-worker/` proxy。如果使用者說「要開始分享了」，先確認這件事，比他要求的功能更優先，要主動提。

### 3. 這個 repo 的邊界不等於 git 的邊界
`撲滿/自動化撲滿/` 和 `撲滿/撲滿-web/` 是**獨立 git repo**（有自己的 GitHub 遠端），被 KANG-agent gitignore。在那裡改東西要在子目錄內 commit/push。另外劇本、LINE 主題這類非程式產出也住在這個 repo——不是所有任務都是寫程式，劇本任務的規則在記憶檔（project_*_drama、feedback_drama_villain_arc）。

## 這套制度最可能怎麼退化，怎麼防

1. **規則通膨**：每次踩坑加三行，一年後沒人讀得完，弱模型只會挑前面幾行看。→ 防法：維護協議的行數上限是硬規則；加新規則時優先「改一條舊的」而不是「加一條新的」。
2. **規則與現實漂移**：專案狀態變了（Python 版刪了、撲滿改名了）但路由表沒更新，之後的 session 信了錯的地圖。→ 防法：發現文件與現實不符時，**當場修文件**，這比手上的任務更急，因為錯的地圖會坑之後每一個 session。
3. **制度變成儀式**：為了照模板派工而派工、為了打勾而打勾，忘了每條規則的動機。→ 防法：每條規則都寫了「為什麼」；如果你發現自己在執行一條說不出為什麼的規則，去讀 [診斷報告.md](診斷報告.md)，還是說不通就照維護協議提修改。
4. **備份目錄變垃圾場**：`制度/備份/` 無限堆積。→ 防法：照[維護協議.md](維護協議.md)第一節，同一檔只留最近 3 份備份。
