# 維護協議：怎麼安全地更新制度檔

> 制度檔清單：根 `CLAUDE.md`、`制度/` 下所有 .md、各專案的 CLAUDE.md。

## 一、改之前

任何制度檔要改，先備份到 `制度/備份/檔名.YYYY-MM-DD.bak`（同日多次改，只留當日第一份）。同一檔最多留最近 3 份備份，更舊的順手刪掉。備份檔永不編輯、永不當作內容來源。

## 二、可以自行改（不用問使用者）

- **事實過時**：路徑改了、專案狀態變了（上線/停用）、部署 URL 換了 → 直接更新，並在該行後面不留痕跡地改正（不要留「原本是…」的註記）。
- **踩坑教訓**：某條規則被證明會誤導 → 在對應檔案修正該條，並照第四節格式記錄。
- **新專案**：在根 CLAUDE.md 路由表加一列＋建立該專案的說明檔。

## 三、動之前必須先問使用者

- 刪掉整份制度檔、或刪掉「危險動作清單」「派工三件套」「判斷準則的誠實條款」這三個核心結構
- 放寬任何安全約束（例：允許公開部署 URL、允許 commit config）
- 改變專案優先順序（寫在根 CLAUDE.md 路由表下方）
- 大幅改寫（超過檔案一半內容）任何制度檔

## 四、踩坑教訓寫回哪裡、什麼格式

坑的教訓寫到**它該生效的地方**，不要集中一本流水帳：
- 專案相關的坑（某 API 的怪行為、部署陷阱）→ 該專案的 CLAUDE.md／README，一行一坑
- 工作方式的坑（派工方式失敗、驗證漏洞）→ `制度/` 對應檔案的對應小節
- 使用者偏好 → 記憶系統（memory 檔），不進 repo

格式（一行式）：
```
- 【坑】做 X 時不要 Y，會 Z。改用 W。（YYYY-MM-DD）
```
必須含觸發情境與替代做法；只寫「小心 Y」等於沒寫。

## 五、精簡時機與方法

- 任何單一制度檔超過 **150 行**、或根 CLAUDE.md 超過 **60 行**，下次動到它時順手精簡：合併重複、刪除已失效的坑（對應功能已不存在）、把細節下放到專案檔。
- 精簡的原則：刪「解釋」不刪「判準」；每刪一條規則要能說出「為什麼現在不需要它」。說不出來就留著。
- 精簡也算「改」，適用第一節備份規則。

## 六、記憶系統的分工

- repo 能記的（程式結構、修過什麼、部署方式）→ 寫 repo 文件，**不寫記憶**
- 跨專案的使用者偏好、工作習慣回饋 → 寫記憶（feedback/user 類）
- 記憶與 repo 文件衝突時：以 repo 文件為準，並更新記憶。
- 記憶索引變長、有重複時，用 `/consolidate-memory` skill 整理。
