# 模型調度守則

> 讀者：在 KANG-agent 工作的主對話模型（通常是 Sonnet）。
> 核心原則：**指揮官不下場**。主對話的 context 是最貴的資源，只放決策與結論，不放原始材料。

## 一、哪些事一律派 subagent（用 Agent 工具）

| 任務 | 派誰 | 為什麼 |
|------|------|--------|
| 掃 repo、找「某功能寫在哪」、跨多檔調查 | `Explore` | 唯讀、便宜，回報檔名:行號＋結論 |
| 查網頁/API 文件、比對多篇資料 | `general-purpose` | 把整頁內容留在 subagent，主對話只收摘要 |
| 批次改檔（同樣的改動套用到 3 個以上檔案） | `general-purpose` | 機械性工作，回報改了哪些檔 |
| 規劃一個多步驟實作 | `Plan` | 回傳步驟計畫與關鍵檔案 |
| Claude Code / API 本身的問題 | `claude-code-guide` | 它會查官方文件，不憑印象 |

主對話**自己做**的事：與使用者對話、做決策、單點小修改（一兩個檔、位置已知）、驗收 subagent 的產出。

例外：如果任務只是「讀一個小檔案回答一句話」，直接讀比派工便宜，不要為派而派。判斷標準：**預估要讀進來的內容超過 ~200 行、或要碰 3 個以上不確定位置的檔案，就派工。這條門檻優先於上表——低於門檻就自己做，上表的「派誰」只在達到門檻時適用。**

## 二、模型選擇（本環境實際可用值）

Agent 工具的 `model` 參數可填：`haiku`、`sonnet`、`opus`（`fable` 只在 Fable session 存在，平常別填）。

- **`haiku`**：機械性、判準明確的工作——grep 式搜尋、格式轉換、批次套用已寫好的改動。
- **`sonnet`**：一般實作、研究、審查。注意：`model` 不填是**繼承主對話的 model**，不是預設 sonnet；要確定用 sonnet 就明填。
- **`opus`**：高風險判斷——架構取捨、難 bug 的假設驗證、安全相關審查、或 sonnet 兩次都做不好的任務。

**誠實標註**：這個 harness 的 Agent 工具**沒有 effort/thinking 參數**可以調；能控的只有 model 與 prompt。想要「更深思考」，方法是換更強的 model、或把任務拆小寫清楚。`/code-review` skill 自己有 low～ultra 的等級參數，那是 skill 的參數，不是 Agent 工具的。

## 三、派工三件套（每次派工的 prompt 必含）

1. **目標與動機**：要達成什麼、為什麼要做（讓 subagent 能自行取捨）。
2. **驗收條件**：完成的客觀判準（例：「列出所有呼叫 syncToCloud 的位置，含行號」「改完後 `node --check` 通過」）。
3. **回報格式**：明確規定回什麼、多長（例：「回報：結論 3 句以內＋檔名:行號清單，不要貼程式碼全文」）。

沒寫這三件就派工＝拿到一坨無法驗收的輸出。現成模板見 [派工模板.md](派工模板.md)。

## 四、高風險判斷的第二意見

以下情況不要單一答案定案：安全相關改動、會動到線上服務的決定、兩個方案難以取捨。

做法（Sonnet 等級可執行）：
1. 派兩個獨立 subagent 用**同一題目、不同切入指示**各給一個答案（例如一個從「最小改動」出發、一個從「長期維護」出發）。
2. 主對話比對兩份答案：一致 → 採用；不一致 → 把分歧點列出來，再派一個 `opus` subagent 只裁決分歧點，或直接問使用者。
3. 裁決理由寫進回覆給使用者看，不要默默選。

## 五、subagent 產出的驗收

- subagent 的回報是**主張，不是事實**。落檔類產出至少抽查一項（開檔看一段）；改碼類產出跑一次驗證指令。
- subagent 失敗或回報模糊：用 SendMessage 追問**一次**（它保有原 context）；再不行就換方式，不要同 prompt 重派第三次。
