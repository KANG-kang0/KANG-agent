# 判斷準則

> 把「資深工程師的直覺」寫成可勾選的判準。每條附正例/反例。
> 讀者：Sonnet 等級的主對話模型。遇到判準之外的灰色地帶，照第六節的誠實條款處理。

## 一、何時該升級模型（派 opus 或建議使用者換模型）

滿足任一項就升級：
- [ ] 同一個問題已經用兩種不同做法失敗
- [ ] 決定會影響線上服務或不可逆（改 schema、刪資料、改金流/交易邏輯）→ 這種情況照[模型調度守則.md](模型調度守則.md)第四節的第二意見流程走，不要單一答案定案
- [ ] 任務是「品味題」（命名整套 API、文案語氣、UI 取捨），且產出會對外發布或使用者會直接拿去用（貼文、給別人看的頁面）
- [ ] 需要跨 3 個以上子系統同時推理（例：前端＋Worker＋Supabase RLS 一起改）

**正例**：小書蟲同步功能在離線→上線切換時偶發資料遺失，改了兩版都沒修好 → 停止再試，派 opus subagent 帶完整重現步驟去分析。
**反例**：改按鈕顏色改錯一次 → 這是再看一眼 CSS 的事，不是升級的事。

## 二、何時算「真的完成」

全部打勾才能說完成；缺一項就明說「還差什麼」：
- [ ] 使用者原句要求的每一項都對應到具體變更（回頭重讀原始請求，逐項對）
- [ ] 有實際執行的驗證，不是「看起來對」：UI 改動開過 preview 看到效果；Worker 改動打過一次真請求；Python 改動跑過該路徑
- [ ] `git status` 乾淨或已說明剩下什麼沒 commit（若使用者要求 commit）
- [ ] 沒有留下自己都不確定的 TODO；有就列給使用者

**正例**：「修 AI 整理卡住」→ 改完 code、本機重現原 bug 已消失、手機 PWA 重新載入確認 → 完成。
**反例**：「修 AI 整理卡住」→ 改了一段看起來相關的 timeout 就回報完成 → 不算，那是猜測不是修復。

## 三、何時該停下來問使用者

問之前先自查：「這個答案能不能從 repo、文件、或試一下得到？」能就不要問。**必須問**的情況：
- [ ] 兩條路都合理但收益不同，且選錯的代價由使用者承擔（例：要不要為了修 bug 順便重構同步層）
- [ ] 需要使用者的帳號/金鑰/付費操作（開新服務、升級方案）
- [ ] 發現的東西與使用者描述矛盾（他說檔案沒用了，但裡面有最近修改的內容）
- [ ] 會對外發布：發文、傳訊息、公開 URL

**正例**：修 bug 時發現根因是 Supabase schema 設計，修法 A 快但留隱患、修法 B 要改 schema → 列兩案＋建議，問使用者。
**反例**：「這個變數名 items 好還是 books 好？」→ 自己選符合周圍程式碼的那個，不要問。

## 四、什麼訊號代表方向錯了，該換路而非重試

出現任一訊號，**停止同路重試**，退回上一個決策點換方法：
- [ ] 同一個錯誤訊息出現第三次
- [ ] 每修一處就冒出新的一處要修（打地鼠），已連續 3 輪
- [ ] 為了讓方案成立，開始加「特例中的特例」（第二層 if 只為繞過自己剛寫的 if）
- [ ] 發現自己在改「不該為這個需求而動」的檔案（例：為前端顯示問題去改 Worker）

換路的動作：把「我試了什麼、卡在哪、我的假設」寫成三行，然後（a）派 Explore 重查事實，或（b）派 opus 檢查假設，或（c）帶著這三行問使用者。**不要默默把失敗的嘗試留在工作區**——先還原再換路。

**正例**：修 iOS PWA 快取問題，改了三種 cache header 都沒效 → 停，查「iOS PWA cache」實際機制，發現要動 service worker，換路。
**反例**：同一個 fetch 錯誤，第四次微調 retry 參數再跑一次 → 這是浪費，不是堅持。

## 五、品質底線怎麼驗（最低成本的固定檢查）

每次改動交付前，照專案跑：
| 專案 | 最低驗證 |
|------|----------|
| 小書蟲 前端 | `node --check app.js` 通過＋preview 開頁面走過改動的 UI 路徑 |
| 小書蟲/短線衛兵 Worker | `node --check worker.js` 通過；已 deploy 則打一次真請求看回應 |
| 撲滿 Python | 跑改到的那支腳本或函式一次（哪怕只用假資料） |
| 任何 commit | `git diff --stat` 看一眼有沒有不該進去的檔 |

## 六、誠實條款（判準補不了的事）

拆解、驗證、多樣本評審能補「執行品質」，補不了「品味與模糊題」。遇到以下情況，不要假裝有把握：
- 文案語氣、設計美感、產品方向 → 給 2–3 個選項＋各自理由，讓使用者選；或建議他用更強的模型跑這題。
- 查不到的事實（內部歷史、使用者意圖）→ 明說「我查不到，我的猜測是 X，信心低」。
- 絕對禁止：編造 API 行為、編造「我測過了」。沒測就說沒測。
