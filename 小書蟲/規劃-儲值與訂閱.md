# 小書蟲規劃：個別使用者的 AI 儲值與訂閱

> 2026-07-07 與使用者定案：**點數制與訂閱制並行**。本檔是實作路線圖，任何 session 要動手前先讀完「階段」一節，照順序做，不要跳。

## 核心答案：點數＋訂閱可以並行，不會互相干擾

前提是兩者收斂到**同一個計量層**，架構長這樣：

```
使用者（Supabase Auth 登入）
   │ 帶 JWT
   ▼
proxy Worker（小書蟲-worker）
   1. 驗 JWT → 得 user_id
   2. 查餘額（先扣訂閱月配點，再扣儲值點）
   3. 餘額夠 → 呼叫 Claude API → 記 usage → 扣點
   4. 不夠 → 回「點數不足」讓前端導購
   ▼
Supabase：credits 帳本 ＋ usage 流水
```

訂閱＝「每月自動發一批會過期的點」；儲值＝「買一批不過期的點」。對計量層來說是同一種東西，只差發放來源與有效期，所以不互相干擾。扣點順序固定：**先扣快過期的訂閱點，再扣儲值點**——這條寫死，別讓使用者的儲值點先被吃掉。

## 資料表（Supabase，加進 supabase-schema.sql）

- `ai_usage`：user_id、動作（ocr/summarize）、tokens、扣點數、時間。RLS：本人可讀，只有 service_role 可寫。
- `credit_ledger`：user_id、變動量（+發放/-消耗）、來源（purchase/subscription/free_monthly）、到期日（儲值點為 null）。餘額＝加總，不要另存一個「餘額欄位」造成兩份真相。

## 階段（嚴格照順序）

| 階段 | 內容 | 前置條件 |
|------|------|----------|
| **0. key 下架**（上架/推廣前**必做**，最優先） | 前端移除 bundled Claude key，所有 AI 呼叫改走 proxy Worker；Worker 加 per-user 基本限流 | 無 |
| 1. 計量 | proxy 驗 Supabase JWT，寫 `ai_usage` 流水；未登入者不能用 AI | 階段 0 |
| 2. 點數帳 | `credit_ledger`＋扣點邏輯＋前端餘額顯示；每月免費額度（登入送 N 點）用 subscription 型發放實作 | 階段 1 |
| 3. 儲值金流 | 見下方「金流的關鍵限制」 | 階段 2 |
| 4. 訂閱 | 定期發點（Stripe subscription webhook 或 IAP 續訂通知 → 寫 ledger） | 階段 3 |

## 金流的關鍵限制（決定上架策略，先讀再選）

- **App Store 上架版**：數位商品（點數/訂閱）**必須走 Apple IAP**，抽成 15–30%，且不得在 app 內引導繞去網頁付款。
- **PWA（現況）**：不受 IAP 限制，可用 Stripe／台灣的藍新・綠界，抽成 ~3%。
- 建議路線：**先在 PWA 驗證「有人願意付」**（階段 0–3 全部在 PWA 完成），確認付費意願後再評估 App Store 上架（iOS 原生版重啟時）。上架不是收費的前提，PWA 就能收。

## 定價（估算，動手前要用當時 API 價格重算）

一次 OCR＋整理約消耗數千 input tokens（含圖）＋數百 output tokens，成本量級約 NT$0.3–1。點數定價抓成本的 3–5 倍起（涵蓋失敗重試與抽成），例如 100 點 NT$149、OCR 一次 5 點、整理一次 3 點。**這段是估算，標註存疑，實作階段 3 前先重算並讓使用者定價。**
