# 小書蟲核心改版計畫：從「讀完的紀念館」到「閱讀時刻」

> 2026-07 Fable 5 最後 session 寫成。設計判斷已定案，執行者是之後的模型（Sonnet 可完成）。
> 每項附「可行性依據」＝已驗證的現有程式碼事實。與[規劃-產品路線.md](規劃-產品路線.md)的關係：本檔取代其中「共讀書櫃」成為下一個主線；點數帳、金流順序不變。

## 一、診斷：為什麼你很喜歡卻久久才打開

不是 bug，是結構。目前所有功能（新增書、OCR、AI 整理、分享卡、年度回顧）全掛在「**讀完一本書**」這個事件上——它一個月才發生一兩次。app 是一座紀念館，紀念館本來就久久去一次。

但愛書人**每天**都在發生的事是：讀到一句話心裡「嗯！」了一下。這個時刻現在沒有去處（或者去了截圖庫、隨手貼 IG 限動就消失）。**改版的全部邏輯：把 app 從低頻事件（讀完）掛到高頻事件（讀到好句子）上。**

## 二、書帳讀者期待什麼（回答你的問題）

會追書帳的人要的是兩件事：
1. **被推坑，但要「真人證詞」**——不是行銷文案，是「一個真實的人讀完之後真的有感覺」。而推坑的最小單位不是書評，是**一句擊中人的金句**：句子是書的預告片，30 字就能讓人決定「我要讀」。
2. **省時間的篩選**——「這本值得我花 8 小時嗎？」所以「推薦給誰」比「內容大意」有用（books 表已有 `recommend_for` 欄位，一直沒被當主角）。

這跟改版方向是同一件事：你為自己隨手留的金句，就是對外最有推坑力的內容。**自留 = 內容生產，零額外成本。**

## 三、四個設計（按價值排序）

### 1. 金句快取（capture-first，本改版的核心）
開 app 第一眼是一顆大大的「✍️ 留一句」：拍書頁或貼文字，**10 秒完成就能關掉**。書不用先建檔——句子先進「收件匣」，之後有空再歸到書上（或用 AI 從照片辨識書名自動猜）。閱讀時的摩擦必須趨近於零，這是成敗關鍵。

**可行性依據**：拍照→上傳管線已有（notes 的 `{uid}/notes/` 同模式）；OCR 摘句用現有 Claude proxy（計量已上線，多一種 `X-Usage-Action: quote_ocr`）；**需要新 `quotes` 表**（id, user_id, book_id **nullable**＝收件匣, text, source_image_path, created_at，RLS 照 books 模式）＋ IndexedDB 加一個 quotes store（books/notes 的本地+雲端雙寫模式照抄，實作前先 grep `saveBookDB`/`toRow` 讀懂現有雙寫）。
**已驗證限制**：現在金句存在 `books.quote_for_card`，一本只能一句——quotes 表就是為了解開這個限制；既有那句在遷移時匯入 quotes，`quote_for_card` 保留當「分享卡選用句」。

### 2. 回音（讓 app 值得「沒事也打開」）
開 app 首屏在「留一句」下方放一張「回音卡」：隨機或按日期抽一句**過去的自己**留的句子＋當時的書。「一年前的今天你在讀《X》，留下了這句」。日記型產品最強的留存不是新功能，是**過去的自己**。

**可行性依據**：純前端（從 quotes/books 抽），零新後端。
**Phase 2（可選）**：Web Push 每週推一句。已驗證**目前沒有 service worker**，iOS PWA 推播需要加 SW＋訂閱管理——工程量中等且有快取翻車前科（之前修過 PWA 快取 bug），所以放後面，先用首屏卡驗證回音有沒有感。

### 3. 公開書架升級成「推坑頁」
既有 `/u/暱稱` 加三件事：(a) 每本書顯示**多句**金句（來自 quotes）＋`recommend_for`「推薦給誰」；(b)「💭 我想讀」計數改名顯示為**推坑成績**（「已推坑 3 人」）；(c) 書名旁加購書搜尋連結（博客來/readmoo 搜尋 URL，不用 API，未來可換聯盟連結變第二收入）。

**可行性依據**：公開頁與 reactions 已上線（2026-07-07）；`shelf_books` view 加欄位可用 `create or replace`（只能加不能刪，已驗證此限制）；quotes 公開需在 view 同模式再開一個 `shelf_quotes` view（安全欄位投影，只投影書架開啟者的句子）。

### 4. 「在讀」狀態（把進行式放進 app）
books 加 `status`（reading/done，預設 done 向下相容）。書架頂部一排「📖 正在讀」，新金句預設掛在正在讀的書上（進一步降低摩擦）。**刻意不做**：進度百分比、閱讀計時、目標打卡——那是自律工具的路，會把愉悅變成 KPI。

**可行性依據**：已驗證 books 表**沒有** status 欄位，`alter table add column` 一行＋前端篩選；IndexedDB 物件無 schema 遷移問題（withDefaults 補預設值的模式已存在）。

## 四、實作階段（每階段可獨立交付）

| 階段 | 內容 | 驗收條件 |
|------|------|----------|
| 1 | quotes 表＋金句快取（拍照/貼字→收件匣→歸檔到書） | 手機實測：從開 app 到存好一句 ≤ 15 秒；離線也能存（上線後同步）；SQL 交使用者執行 |
| 2 | 首屏改版：「留一句」置頂＋回音卡 | 有 ≥1 句時開 app 必見回音；點回音跳到該書 |
| 3 | 推坑頁：多金句＋推薦給誰＋推坑成績＋購書連結 | 無痕開 `/u/kang-reads` 看到金句與「已推坑 N 人」 |
| 4 | 在讀狀態 | 加書時可選「正在讀」，金句預設掛在讀中的書 |
| 5（可選） | Web Push 週回音 | iOS 加主畫面後能收到；退訂可用 |

規則：每階段完成回本檔打 ✅＋一行做法；UI 文案（按鈕字、回音卡語氣）產 3 版給使用者選——這是品味題，不要自己定稿。AI 相關新動作都要過既有計量（登入＋扣 `ai_usage`）。

## 五、砍掉清單（防止未來 session 加回來）

- 陌生人動態牆、留言——[規劃-產品路線.md](規劃-產品路線.md)已禁，重申
- 書評長文編輯器——長文屬於 Threads（用 /reading-note skill），app 只管時刻與句子

## 六、誠實條款

- 全部階段在 Sonnet 能力內；最大風險不是技術而是**首屏改版的手感**（按鈕大小、動線），實作後必須真機（iPhone PWA）走一遍並讓使用者摸過再收工。
- 「回音有沒有感」無法事先驗證——上線兩週後問使用者開 app 頻率有沒有變，沒變就把回音換成別的鉤子（如「這本書你留了 5 句，要不要做成圖卡」），不要加碼推播。
