# 小書蟲核心改版計畫：從「讀完的紀念館」到「閱讀時刻」

> 2026-07 Fable 5 最後 session 寫成。設計判斷已定案，執行者是之後的模型（Sonnet 可完成）。
> 每項附「可行性依據」＝已驗證的現有程式碼事實。與[規劃-產品路線.md](規劃-產品路線.md)的關係：本檔取代其中「共讀書櫃」成為下一個主線；點數帳、金流順序不變。

## 一、診斷：為什麼你很喜歡卻久久才打開

不是 bug，是結構。目前所有功能（新增書、OCR、AI 整理、分享卡、年度回顧）全掛在「**讀完一本書**」這個事件上——它一個月才發生一兩次。app 是一座紀念館，紀念館本來就久久去一次。

但愛書人**每天**都在發生的事是：讀到一句話心裡「嗯！」了一下。這個時刻現在沒有去處（或者去了截圖庫、隨手貼 IG 限動就消失）。**改版的全部邏輯：把 app 從低頻事件（讀完）掛到高頻事件（讀到好句子）上。**

## 二、書帳讀者期待什麼（回答你的問題）

會追書帳的人要的是兩件事：
1. **被推坑，但要「真人證詞」**——不是行銷文案，是「一個真實的人讀完之後真的有感覺」。而推坑的最小單位不是書評，是**一句擊中人的金句**：句子是書的預告片，30 字就能讓人決定「我要讀」。
2. **省時間的篩選**——「這本值得我花 8 小時嗎？」所以「推薦給誰」比「內容大意」有用（books 表已有 `recommend_for` 欄位，一直沒被當主角）。

這跟改版方向是同一件事：你為自己隨手留的金句，就是對外最有推坑力的內容。**自留 = 內容生產，零額外成本。**

> **v2 定案（2026-07-09，Opus plan mode 與使用者逐題確認）**：以下第三節起為最終決策，取代舊版。四個關鍵決定：①首屏核心＝金句牆（不是回音卡）②只砍「讀書當下」欄位 ③砍靜態 HTML 匯出 ④不做「在讀狀態」。

## 三、設計（按價值排序）

### 1. 金句系統：quotes 表 + 快取 + 金句牆（本改版核心）

**金句快取（capture-first）**：開 app 頂部釘一顆大大的「✍️ 留一句」：拍書頁或貼文字，**10 秒完成就能關掉**。書不用先建檔——句子先進「收件匣」（book_id 為 null），之後有空再歸到書上（或用 AI 從照片辨識書名自動猜）。閱讀時的摩擦趨近於零，這是成敗關鍵。

**金句牆＝新的 landing view**：開 app 第一屏就是一條 feed，列出你所有書的金句（新→舊，含「來自《書》」）。這是「沒事也想打開」的那個畫面——你自己的畫線精選。點任一句可跳到該書、或直接做成圖卡分享。
- **回音（低優先，near-free）**：金句牆加一顆 shuffle 鈕，隨機或偏向「N 年前的今天」抽舊句。純前端，不是獨立畫面（使用者選了金句牆而非回音卡當首屏，回音降為牆內模式）。

**可行性依據**：拍照→上傳管線已有（notes 的 `{uid}/notes/` 同模式，改用 `{uid}/quotes/`）；OCR 摘句用現有 `callClaude(body, action)`，`action='quote_ocr'`（計量已上線）；**需要新 `quotes` 表**（id, user_id, book_id **nullable**＝收件匣, text, source_image_path nullable, created_at，RLS 照 books 模式）＋ IndexedDB 加一個 quotes store（books/notes 的本地+雲端雙寫模式照抄：先讀 `saveBookDB` app.js:130、`toRow` app.js:~240、`withDefaults` app.js:449）。render()（app.js:1725）加 `quoteWall` 分支並設為預設 landing；renderNav（app.js:1778）改三顆：✍️金句牆／📚書架／📊年度回顧。
**已驗證限制**：現在金句存在 `books.quote_for_card`，一本只能一句——quotes 表解開此限制；既有那句遷移時匯入 quotes，`quote_for_card` 保留當「分享卡選用句」。

### 2. 公開書架升級成「推坑頁」

既有 `/u/暱稱`（2026-07-07 已上線）加四件事：
- (a) 每本書顯示**多句**金句（來自 quotes）＋`recommend_for`「推薦給誰」
- (b)「💭 我想讀」計數對外顯示為**推坑成績**（「已推坑 3 人」），資料來自既有 `shelf_reactions`
- (c) 書名下加**購書連結**：直接用既有 `buyLinks(title)`（博客來/誠品/讀冊/Readmoo，**已存在，不要重寫**），補進 `publicBookCell`
- (d) **分享回流閉環**：金句卡（`renderShareCardModal`/`renderSharePreview`）底部加一行「全書金句 → /u/暱稱」，只有已開公開書架時才帶。讓高頻的分享行為回灌書架流量。

**可行性依據**：`shelf_books` view 用 `create or replace` 加欄位（已驗證此限制）；quotes 公開需同模式新增 `shelf_quotes` view（安全欄位投影，只投影書架開啟者且該書所屬的句子）。

## 四、實作階段（每階段可獨立交付）

| 階段 | 內容 | 驗收條件（end-to-end） |
|------|------|------------------------|
| 0 瘦身 | 刪靜態 HTML 匯出、移除「讀書當下」輸入 UI | `node --check` 過；preview 開既有書 detail 正常載入；設定裡不再有「產生公開書架網頁」 |
| 1 | quotes 表＋IndexedDB store＋金句快取（拍照/貼字→收件匣→歸檔） | SQL 交使用者執行；手機實測開 app→存一句 ≤ 15 秒；離線可存、上線後同步；anon 查 quotes 回 200 空陣列 |
| 2 | 金句牆＝landing＋三顆 nav＋回音 shuffle | 開 app 首屏即金句牆；有 ≥1 句時 feed 顯示；點句子跳到該書 |
| 3 | 推坑頁：多金句＋推薦給誰＋推坑成績＋buyLinks＋分享卡帶 shelf URL | 無痕開 `/u/kang-reads` 看到多句金句、「已推坑 N 人」、購書連結 |

規則：每階段完成回本檔打 ✅＋一行做法並 commit+push；UI 文案（留一句按鈕字、金句牆空狀態、回音語氣）產 3 版給使用者選——品味題，不要自己定稿。AI 相關新動作都要過既有計量（登入＋扣 `ai_usage`）。

## 五、砍掉清單（防止未來 session 加回來）

- **靜態「公開書架網頁」HTML 匯出**（`exportPublicShelf` app.js:1505＋按鈕 app.js:2767）——已被 /u/暱稱 活網址取代，兩個功能同名一個是死檔
- **「讀書當下」輸入 UI**（detail view app.js:2413-2417）——使用者確認幾乎不填；**只拿掉輸入框，保留 DB 欄位與匯出**（reading_context 欄位、withDefaults、md/JSON/caption 匯出都留著，避免既有資料遺失）
- **「在讀狀態」**——與 capture-first 收件匣重複（有未歸檔金句的書＝在讀中），且 reading→done 生命週期是把閱讀變 admin 的陷阱
- 閱讀進度％、計時器、連續打卡 streak——把愉悅變 KPI，違背產品靈魂
- 陌生人動態牆、留言——[規劃-產品路線.md](規劃-產品路線.md)已禁，重申
- 書評長文編輯器——長文屬於 Threads（用 /reading-note skill），app 只管時刻與句子

## 六、誠實條款

- 全部階段在 Sonnet 能力內；最大風險不是技術而是**金句牆與留一句的手感**（按鈕大小、動線、10 秒摩擦），實作後必須真機（iPhone PWA）走一遍並讓使用者摸過再收工。
- 「回音有沒有感」「金句牆會不會提高開啟頻率」無法事先驗證——上線兩週後問使用者開 app 頻率有沒有變，沒變就換鉤子（如「這本你留了 5 句，做成合輯圖卡？」），不要加碼推播。
